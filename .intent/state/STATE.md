# File manager installation and adaptation map

## Workspace operation convention

Use the [root operation table](../../README.md#workspace-operations) for `build`, `typecheck`, `setup`, `inspect` and `remove`. The repository root owns development tools, scripts and this intent package; installable artifacts live under `packages/`. Select `DSH_CHECKOUT`, and explicit `DSH_HOME`/`DSH_PROFILE` for profile operations. Setup and removal inspect unless passed `--install` or `--remove`; inspect never mutates. Preserve existing plugin transactions, Host ownership and separate service activation. Build/typecheck/test invoke prepared local Node tools without installing dependencies.

Keep independent repository and package versions. Require compatible API ranges, not equal versions; optional cooperation is not a required dependency. Distribute MIT license text with each package and retain copyright attribution. Record selected installations, verification evidence and historical implementation gaps in [LOG](../logs/2026-09-07-standardized-workspace-operations.md); this map owns intended effects and reusable operations.

Use this document as the installation prompt: establish the selected environment, adapt the supplied implementation to its public capabilities, and deliver the product behavior below. Refine the map from user feedback and observed Host behavior; source symbols and package placement are adaptation references, not frozen interface choices. Record installation observations, implementation debt and validation results in local logs: [independent feature integration](../logs/2026-09-06-independent-feature-dependencies.md) and [trash/action integration](../logs/2026-09-07-trash-and-floating-actions-integration.md).

## Intent

Provide an authenticated DeepSeek Harness Web file manager for browsing and editing the service process's user-visible filesystem. The browser UI uses Host process permissions and does not inherit agent filesystem confinement, sandbox approval, or tool policy. A Session cwd selects only the initial location; users may navigate elsewhere.

## Installation map

### Required capabilities and ownership

| Feature | Required capabilities | Ownership and optional cooperation |
| --- | --- | --- |
| Sidebar | Harness layout APIs | Layout, groups, tabs, previews, persistence and instance lifecycle only; no filesystem or feature-opening policy. |
| Viewer | Sidebar and the shared authenticated UI filesystem provider | Owns the `filesystem` source, supported-file opening, text/image handlers, shared documents and drafts. Requires neither manager nor Links. The editor stays an internal plain dependency, not a separately chosen user feature. |
| Manager | Sidebar and the same shared provider | Owns the tree, directory opening, navigation, mutations and browser transfers. Requires neither viewer nor Links; optional file-drop adds region-based drag upload, while file clicks use the common Host opening entry. |
| Optional file-drop | Harness Client module/service APIs | Owns native-file event routing and exclusive DOM-region targeting. Manager owns its region, SVG/blurred overlay and upload intake; Chat owns its own intake and presentation. The standalone plugin requires neither manager, sidebar nor Viewer. |
| Shared filesystem package | Authenticated Harness UI/Remote APIs | Neutral service definition, one Node provider and generated Remote declarations; Session-relative resolution, metadata, text/bytes and revision-guarded saves. Build and distribute it independently of feature packages. The independent `@dsh-external/dsh-user-files` package is distributed from the existing Links repository and is not a dependency on manager UI. |
| Optional Links toggle in the shared package | Shared filesystem access and Host text-link/opening APIs | Recognizes and confirms paths in Markdown inline code. Requires no sidebar, viewer or manager. Its toggle controls path decoration only; filesystem access and original session-file links remain available when disabled. |

Authenticated user filesystem operations retain service-process permissions, independently of agent `ctx.fs`, sandbox and approval. The shared provider owns path resolution and one canonical-resource publication queue for text and byte saves, including revision checks; viewer documents own browser synchronization, not disk publication. Viewer owns the `filesystem` source and `resourcePollIntervalMs`; manager owns `directoryPollIntervalMs`, tree state and mutations.

All file clicks, including Chat links and manager rows, use the Host's common opening entry, represented by `chat/open-workspace-file` in the supplied sources. Viewer handles supported files and manager handles directories. Unhandled requests delegate to the native opener on the service-process machine; errors after a handler takes responsibility propagate without native fallback. Preserve preview, pin and open-to-the-right intent without exposing viewer internals to other features.

### Adapt and install in the selected environment

1. Select explicit `DSH_CHECKOUT`, `DSH_HOME` and `DSH_PROFILE`. Read the selected Host's instructions, profile composition, manifests, actual resolution targets and existing adaptation receipts. Preserve unrelated plugins, user configuration, sidebar layout and browser drafts. Use the requested feature combination to select dependencies; cooperation with another feature is not permission to require its installation.
2. Compare the selected Host's actual authenticated Remote, Session path metadata, Client module/slot registration, sidebar lifecycle and common opening APIs with the supplied [manifest](../../packages/dsh-file-manager/package.json), [Bundle](../../packages/dsh-file-manager/cordis.patch.yml), [Client registrations](../../packages/dsh-file-manager/src/client/index.ts) and [filesystem implementation](../../packages/dsh-file-manager/src/filesystem.ts). Adapt names and interfaces to the supported Host while preserving the behavior below. Use one opening chain and one filesystem provider, not parallel compatibility implementations. Existing equivalent Host capabilities need no duplicate patch; attribute each necessary adaptation before applying it and retain changes owned by other plugins.
3. Inspect the Host's declaration and Remote generators, including external-project support such as Typert `externalProjectReferences`, and its source-launch requirements. Read the [repository build guide](../../README.md#build-and-test) and actual scripts before choosing commands. Build the selected Host declarations/generator, then the provider and feature Host/Remote/Client artifacts as their dependency graph requires. Use explicitly selected repository tools and compatible APIs; a historical package version or sibling checkout path is not an environmental requirement.
4. Resolve one independently distributed shared provider for all selected consumers. Declare compatible peer/API ranges and development dependencies; keep package versions independent without equal-version checks. Reuse a provider satisfying all consumer ranges, report incompatible ranges explicitly, and avoid duplicate provider rows or Remote namespaces. Viewer/editor form one user feature; manager and Links remain independent options. Local path overrides may support development without requiring neighbouring repositories for normal builds.
5. Read [setup](../../scripts/setup.sh) and [uninstall](../../scripts/uninstall.sh) before execution and verify their actual dependencies, flags, scope and effects against this map. Treat them as tools to adapt, not authorities that can turn a historical prerequisite into a feature requirement. Install the selected feature and needed shared artifacts through the Host's supported plugin transaction, preserving complete configuration rows and effective settings. Keep resource polling under viewer and directory polling under manager; preserve Links enablement and explicit external-opening preferences when adapting an existing profile.
6. Inspect manifest, lockfile, exact installed package targets, Bundle membership, generated Remote declarations and Client rows after the transaction. Cold-start an isolated profile with the selected feature combination before activating a user's profile. Exercise the behavior and failure conditions below; a successful package build or script inspection alone does not establish a working installation. Setup must not restart services implicitly.
7. Remove only the selected feature's owned contributions and dependencies. Retain sidebar and the shared provider while other consumers need them; check remaining consumer manifests before removing shared capabilities. Inspect residual resolutions, rows and generated browser entries. Do not delete user files, browser preferences or drafts, and do not reverse an entire historical Host patch merely because one feature is removed.

### Combination checks

With sidebar and the shared provider, viewer alone must read and edit supported remote files reached through original session-file links; manager alone must browse and mutate directories and send unhandled file clicks to the native opener. With both features, files reach viewer and directories reach manager independent of installation order. Links works without either feature or sidebar; disabling it stops automatic path decoration and discovery queries while retaining filesystem access and original session links. Handler failures remain visible without fallback, and removal of one consumer leaves the others usable.

## Product behavior

- The `fileManager` Host Remote uses Node filesystem APIs and configurable GNU `mv` for no-clobber moves without copy/delete fallback. It lists directories lazily, follows symbolic links for navigation and resource identity, and retains the user-visible link path for move and deletion actions.
- The Files launcher opens one tree instance per Session in the right-sidebar workbench. Address navigation, manual refresh, hidden entries, create, move/rename, and configured deletion are available from the tree. Non-overlapping automatic polling refreshes only the current and expanded loaded directories, stops on superseding work or disposal, retains reachable expansion and selection, and exposes per-directory failures without discarding the last successful listing.
- The path input stays visible and navigates on Enter. New file, New folder, optional Upload, Refresh, and More float over the first list row (`..` outside filesystem root) at rest while remaining outside the scroll container, and appear on hover or keyboard focus. Touch devices keep More visible as the expansion target and place the other actions inside it. Narrow panes progressively move Refresh, New folder, and New file into More, without a separate persistent toolbar.
- More holds browser-persisted Show hidden files, Move to trash when deleting, and Filter switches plus Open trash. The filter input appears only while enabled and retains its query while disabled; disabling it stops filtering. Queries match names and relative paths only in the loaded tree. Matching descendants retain their ancestors, and changing filter visibility does not change expansion, selection, or the scroll container.
- The sidebar persists a v2 tree descriptor containing the current root, expanded directories, selection, and filter query. Restoration accepts v1 navigation without letting its hidden-entry value replace browser preferences, and rebuilds those loaded directories. File-manager state is released only by the sidebar's committed close notification, never by close confirmation.
- Creating and moving reject an existing target. Each row has one Delete action. Outside the home trash, the menu's Move to trash when deleting switch selects recoverable removal without confirmation or permanent removal with exactly one ordinary confirmation. This manager preference persists in browser storage across trees and reloads; Host deleteMode initializes it only when no valid preference exists. Tree restoration cannot replace it. Trash receives literal paths without glob expansion and never falls back to deletion. Host deletion rejects filesystem root and unlinks symbolic links instead of recursively traversing their targets.
- Open trash uses the installed Linux provider's `xdg-trashdir` resolver to navigate to its home `files` directory. It creates nothing and excludes other-volume trash and original-name reconstruction. The tree identifies this scope and possible generated filenames. Delete within the home trash root or any subdirectory is always permanent and requires one explicit confirmation, regardless of browser preference. The Host protects root/files/info themselves, including paths through parent aliases, and rejects deletion on provider lookup failure; unsupported platforms retain ordinary deletion behavior.
- Restore is available only for direct files children and returns the entry to its own regular, non-symlink `.trashinfo` record's single percent-decoded absolute original path outside trash, using the configured no-clobber move and shared mutation queue. Missing/malformed records, nested entries, missing destination parents and occupied targets fail without removing the record or entry. Successful restoration or permanent deletion of a direct child cleans its matching record; a cleanup failure reports the completed file operation and remaining record. Missing or inaccessible directories and unsupported platforms, including WSL, show explicit errors while retaining the current tree.
- The shared provider's read-only resolveMany operation preserves each input path and its order, including duplicates, with individual metadata or error results. maxResolveBatchSize limits each request before path resolution; cancellation rejects the request. Batch resolution shares single-path metadata resolution and reads no file content.
- The shared provider backing viewer's `filesystem` source exposes bounded metadata, bytes, and text without reading content during listing. Text and byte limits are configured separately. Byte reads accept arbitrary bounded regular-file bytes and exact byte saves use the guarded publisher. Text reads reject malformed UTF-8 and NUL bytes, canonicalize CRLF and CR to LF, and retain EOL metadata in the opaque revision. Saves restore the loaded EOL convention, including an exact mixed-EOL pattern for existing lines, and preserve terminal-newline presence represented by editor text.
- Revisions contain exact content SHA-256 and file stat values. Plugin writes to one canonical resource are serialized. Save stages a same-directory file and rechecks the exact loaded revision immediately before atomic rename.
- The ordinary filesystem cannot provide strict compare-and-swap against an uncooperative external writer between the final recheck and rename. `supportsConditionalSave` means guarded optimistic publication within this stated limit, not universal atomic CAS.
- Viewer-owned text and byte source watches poll only while subscribed, wait for each read before scheduling the next, and abort/clear their timer on disposal.
- Regular-file links from the tree route through the central resource-opening service. A tree click selects and persists the visible row path while opening the canonical resource; single click requests a preview in the group to the right of the tree, and double click requests a permanent tab. A new attempt clears the preceding open error, and superseded preview failures stay hidden. Directory selections open the tree. Automatic Chat path recognition belongs to optional Links; manager handles directories in the common Host opening chain and delegates file handling.

## Acceptance criteria

- `MANAGER-001`: Session cwd opens as the initial canonical directory, while absolute navigation outside it remains available.
- `MANAGER-002`: Tree listing follows usable symlinks, supports hidden entries and lazy expansion, and routes regular files through the central resource opener to a stable group right of the tree; single click previews and double click pins.
- `MANAGER-003`: File and directory creation plus move/rename reject existing targets. Outside home trash, one Delete button follows the browser-persisted Move to trash preference: trash has no confirmation or fallback, and permanent deletion uses one confirmation. Restoring a tree cannot reset the preference. Both modes reject filesystem root, and permanent link deletion cannot traverse the target. Trash descendants require confirmed permanent deletion; root/files/info themselves are protected. Restore direct files children from valid records without clobbering original paths; occupied targets preserve entry and record.
- `MANAGER-004`: Bounded byte loading accepts binary and NUL-bearing regular files. Text loading rejects NUL-bearing, malformed UTF-8, excessive, and non-regular content; EOL and terminal-newline semantics survive an unchanged save.
- `MANAGER-005`: A changed external revision and a second plugin save from the same base fail without clobbering the current file.
- `MANAGER-006`: Viewer resource polling and manager directory polling each avoid overlapping reads within their own lifecycle, stop after disposal, and cannot publish late results. Directory changes refresh the current and expanded loaded tree while retained expansion, selection, filtering, scroll container, and explicit failures remain observable.
- `MANAGER-007`: Build emits Host, Remote, declarations, and browser Client artifacts; setup requires explicit checkout/home/profile and never restarts a service.
- `MANAGER-008`: Loaded-tree filtering matches names and relative paths, retains matching ancestors, performs no recursive filesystem read on input, and clearing it restores the unfiltered loaded tree.
- `MANAGER-009`: Tree selection uses the central resource-opening service; external directory selections use the Files launcher. Chat and tree file clicks share the Host opening chain; Links is optional.
- `MANAGER-010`: Browser reload reconstructs the tree's current root, reachable expansion, selection, and filter query while the menu preferences remain browser-owned. Legacy v1 trees remain restorable without overriding saved preferences. A stale, vetoed, or superseded close attempt cannot release feature state, and late directory reads cannot checkpoint after committed removal.
- `MANAGER-011`: resolveMany accepts up to maxResolveBatchSize paths, returns separate ordered successes and failures without content reads, and rejects larger or cancelled requests.
- `MANAGER-012`: The path input stays visible without a label or Go button; creation, optional upload, refresh and More icons float outside the scroller, align with its first row at rest, and remain available through hover, keyboard, touch, and progressive narrow-pane overflow. More remembers three checked preferences. Disabling Filter removes its input and stops filtering while preserving the query.
- `MANAGER-013`: Open trash browses the provider-selected Linux home files directory and describes its deletion and restoration scope. Unsupported platforms, absent directories, provider failures, and superseded lookups cannot navigate to an invented path or create a directory.

### Install and verify browser transfers

Use sidebar >=0.0.1 for layout and the selected Host's public `remote.$host.isLoopback` and `session.canOpenWorkspacePath()` capabilities. Upload and Download appear unless both facts report usable local native opening. Keep the manager's required `connection` and `webServer` services in the Web composition; use their authenticated request check for raw binary routes and shared user-files for Session path resolution and publication serialization. Keep all transfer filesystem operations manager-owned without introducing a provider dependency on manager or a Viewer requirement.

Install `@dsh-external/dsh-file-drop` ^0.1.0 independently only when drag upload is desired. Keep it an optional manager peer, outside manager's required Bundle and Client injection list. Subscribe to `ctx.fileDrop` without awaiting its availability, attach each mounted manager panel's content region, and dispose the region when the provider or panel is removed. Late provider activation must enable existing panels. Manager supplies the full content-area blur/tint overlay, file/folder upload SVG, localized upload invitation and current destination; tabs remain outside the region. Busy or unready trees show a blocked invitation and reject the drop. Without this optional provider, verify browsing and upload/download buttons remain usable and no manager drag overlay appears.

Preserve or choose `maxUploadBytes` in the complete manager config row; the supplied Bundle uses 10 GiB per file. Follow [the transfer reference](../../README.md#browser-transfers) to forward the exact transfer route through a reverse proxy with matching request limits, streaming and deployment-appropriate timeouts. Build the sidebar and optional file-drop declarations before manager. After authorized activation, choose binary and empty files, upload by button and, when file-drop is installed, by a drop into a navigated manager panel, download with original names, and compare bytes. Expanded subfolders must not redirect uploads. Retry an existing filename and verify it remains unchanged. Cancel or close during an unfinished upload and check that no final partial file or staging directory remains; already completed files in a batch remain published. An inactive group's tab must never receive another group's dropped files.

- `MANAGER-014`: Native-unavailable connections expose Upload beside creation and regular-file Download immediately left of Delete, including narrow-pane/touch access. Raw binary transfers retain original filenames and avoid full-file JSON/base64 buffering. Upload rejects existing entries and enforces the configured bound, cleans unfinished staging on cancellation, and shares one pipeline for file selection and optional manager-region drops. With file-drop present, only the hovered panel shows its manager-owned upload overlay and destination; provider removal clears it without disabling ordinary file operations. Filtering retains its semantics without helper text.

### Verify trash and floating actions

Use disposable fixtures under the selected Host user. Open trash and scroll a long tree: directory actions remain at the top of the tree area, with hover/focus/touch and narrow-pane access. Navigate into a trashed directory and to its parent trash root; Delete must request one permanent confirmation even when Move to trash is checked, and declining must retain the item. Attempts to remove root/files/info must fail. Restore a direct files child with a percent-encoded original name, then repeat with an occupied original path and verify that both trashed data and its record survive. Check malformed/missing records and provider failures remain visible. Rebuild through the normal Host → Remote → Client generator order so `fileManager/restore` is available; preserve complete configuration rows and the independently installed shared provider.

## Non-goals

- Agent tool access, model-visible filesystem context, a bundled binary editor, recursive content search, filesystem ACL management, or a universal cross-process transaction protocol.
- Implicitly targeting a live profile, restarting a service or publishing through setup, or claiming user acceptance from repository checks.

## Concrete configuration cutover

Install one `@dsh-external/dsh-user-files` Bundle from the Links repository. Move effective manager `maxResolveBatchSize`, `maxTextReadBytes` and `maxByteReadBytes` into its complete config row. Move effective `resourcePollIntervalMs` into the complete viewer row without changing the value or other fields. Retain manager `directoryPollIntervalMs`, `deleteMode`, `moveCommand` and `maxUploadBytes`. Preserve old Links `openMode` as shared common opening policy and set shared `enabled: true` when replacing an enabled resource-links installation. New shared installations default Links to false. Remove the old resource-links Bundle and source/content registrations in the same candidate combination; do not maintain two providers.

Manager setup uses the shared package's `install` helper to reuse a compatible provider or add it in the same plugin transaction. Normal dependencies use compatible version ranges. For local builds, `install:local` accepts `DSH_USER_FILES`, `DSH_SIDEBAR` and optional `DSH_FILE_DROP` package directories or tarballs without persisting sibling paths. Manager uninstall retains both shared services. User-files owns the common file-opening and Markdown path-link Host adapter and guards its removal against remaining consumers; manager owns no Host patch.
